# ADR 0001：方案 A 的自研与复用边界

日期：2026-10-02

## 决策

采用小型文化墙专用前后端，不 fork GPT Image Playground，不依赖旧的 `D:\zcode1` 脚本。旧脚本仅用于确认中转站的 OpenAI Images 兼容行为。

## 自己实现

- 文化墙需求输入、参考素材和风格预设；
- 最小结果页和浏览器本地历史；
- 仅监听本机的 Node 服务端；
- 服务端密钥、上传限制、提示词装配与结果落盘；
- 文化墙领域文案和后续生产化入口。

## 吸收现有项目经验但重新实现

- `/v1/images/generations` 与 `/v1/images/edits` 双路径；
- URL 和 `b64_json` 两种结果归一化；
- 超时、错误状态和结果持久化；
- 参考图继续生成的交互；
- 协议层单元测试。

## 暂不复用

- 浏览器内供应商和 API Key 管理；
- Zustand 全局状态树和 IndexedDB schema；
- Responses/SSE、分享广场、导入导出；
- 蒙版编辑器、批量任务、提示词库和通用模型设置 UI。

## 原因

GPT Image Playground 的协议能力较成熟，但通用工作台的数据模型和 UI 远大于本阶段。直接 fork 会先产生删减、安全迁移和品牌重构成本。当前中转站已经通过旧脚本证明兼容 OpenAI Images，因此薄服务端足以验证首版流程。

后续只有出现以下需求时，才重新评估抽取其具体模块：局部蒙版编辑、复杂失败重试、多供应商动态切换、离线大型图库。
