# 生图 MVP 开源方案调研

日期：2026-10-02

## 结论先行

第一版可以做一个本地运行的简单生图网站，用于展示、推销和收集客户反馈，但它应被明确定位为“获客验证版”，不能替代后续的“效果图 → 可编辑／可生产资产”研究。

推荐路线是：**新建一个很小的文化墙专用前后端，借用成熟开源项目的协议适配和任务处理思路，不直接照搬整套通用生图工作台。**

首版只保留：提示词、参考图、少量预设、真实生图、历史结果、下载和继续修改。登录、付费、积分、Agent、无限画布、素材广场、批量并发、SVG 和生产文件都不进入首版。

## iToo Image 页面拆解

用户提供的 `api.itoo.me/custom/...` 页面本身是 API 网关中的自定义页面容器，实际嵌入的是 [iToo Image](https://img.itoo.me)。公开前端资源显示其为 Next.js 应用，已经覆盖：

- Agent 对话与意图识别；
- 文生图、参考图编辑及多模型切换；
- 比例、尺寸、质量和并发参数；
- 图片／提示词素材库；
- 反推提示词、局部编辑、GIF、无限画布等扩展能力；
- `/api/nova/*` 任务和代理接口。

它适合作为交互参考，但不适合按当前体量复制。首版真正值得借鉴的是：

1. 输入和结果在同一页完成；
2. 参考图上传与提示词并列，而不是隐藏在复杂设置中；
3. 生成结果可以继续作为下一轮参考；
4. 长任务有清晰的进行中、成功、失败状态；
5. 模型与供应商配置和普通用户操作分离。

不建议首版复制顶部的 Agent、视频、无限画布、UI 模式、素材库、反推提示词和 GIF 等导航。这些功能会掩盖文化墙场景本身。

## GitHub 候选项目

### 1. GPT Image Playground：最接近，但不能原样上线

仓库：[insistanan/GPT_Image_Playground](https://github.com/insistanan/GPT_Image_Playground)，MIT。

优点：

- React、TypeScript、Vite，依赖较少；
- 已支持 Images API、Responses API、参考图编辑和局部蒙版；
- 有多供应商、任务状态、历史画廊、IndexedDB 和导入导出；
- 协议层有测试，本次本地验证为 6 个测试文件、59 个测试全部通过，生产构建成功；
- 代码中已有请求规划、流式／JSON 降级和结果归一化，可作为协议适配参考。

问题：

- 功能远超首版需求，直接 fork 会带入大量画廊、分享、分类和设置代码；
- API Key 和供应商配置会被持久化到浏览器状态；
- 数据导出清单包含供应商配置；
- 直连模式会让调用凭证出现在浏览器侧；
- 本地开发代理支持动态目标地址，不应直接当作公网生产代理。

可复用方式：提取协议适配、任务状态、图像输入和相关测试，重新接到我们自己的服务端代理；不保留其浏览器密钥管理和完整通用 UI。

### 2. RoomGPT：适合参考最小产品流程

仓库：[Nutlope/roomGPT](https://github.com/Nutlope/roomGPT)，MIT。

它的核心流程是“上传空间照片 → 选择风格 → 调用服务端 API → 比较和下载结果”，而且公开版本刻意去掉了账号和付费。这个产品结构与文化墙获客版很接近。

局限是代码较老、绑定 Replicate 和外部图片存储，不能直接满足中转站、多参考图和后续局部编辑需求。适合借鉴页面流程，不适合作为长期代码底座。

### 3. Vercel AI SDK：可选的供应商抽象层

仓库：[vercel/ai](https://github.com/vercel/ai)，Apache-2.0。

其当前代码包含图片生成、图片编辑和多图编辑示例，并提供统一供应商架构。若中转站严格兼容 OpenAI Images／Responses，可减少协议代码。

风险是 SDK 更新快，而不同中转站往往只兼容部分参数。选择它时必须依据实际安装版本的文档和中转站实测，不能假设所有 OpenAI 参数都可用。

### 4. LiteLLM：多供应商网关，首版可能过重

仓库：[BerriAI/litellm](https://github.com/BerriAI/litellm)，核心部分 MIT。

适合以后统一多个供应商、限流、日志、成本和故障切换。若首版只有一个中转站，再增加 Python 网关会多一层部署和排错成本，暂不推荐。

### 5. ComfyUI／InvokeAI：模型工作流后端，不适合获客首版

- [ComfyUI](https://github.com/Comfy-Org/ComfyUI)：GPL-3.0，适合复杂本地工作流和可控生成。
- [InvokeAI](https://github.com/invoke-ai/InvokeAI)：Apache-2.0，成熟创作引擎和 WebUI。

只有在决定本地部署模型、ControlNet、蒙版修复或固定工作流后才值得接入。首版接中转站时采用它们会明显扩大安装、显存和运维范围。

### 6. 后续生产化候选组件

这些项目不进入简单生图首版，但与已记录的后续方向有关：

- [visioncortex/vtracer](https://github.com/visioncortex/vtracer)，MIT：位图矢量化技术验证；
- [fabricjs/fabric.js](https://github.com/fabricjs/fabric.js)，MIT：对象化画布和 SVG 导入导出；
- [konvajs/konva](https://github.com/konvajs/konva)，MIT：交互画布与设计编辑器；
- [imgly/background-removal-js](https://github.com/imgly/background-removal-js)，AGPL-3.0：浏览器抠图能力，但商用整合前必须评估 AGPL 义务；
- [Monet](https://github.com/Monet-AI-Editor/Monet)，MIT：其“结构化项目 + 确定性工具 + Agent 控制”思路可作为远期生产化工具参考，但它是面向 macOS 的大型视频／画布应用，不适合直接改造首版。

## Skill 调研

OpenAI 官方 curated skill 中没有可直接生成“文化墙生图网站”的现成 skill。当前有帮助的能力为：

- 已内置的 `imagegen`：用于制作演示素材和验证提示词，不是网站运行时后端；
- `playwright`：开发后做本地端到端测试；
- `security-best-practices`：检查服务端密钥、上传和代理安全；
- [vercel/ai 的 `use-ai-sdk` skill](https://github.com/vercel/ai/tree/main/skills/use-ai-sdk)：如果选择 AI SDK 路线，可在后续安装；它要求以实际安装版本的本地文档为准。

GitHub 上能搜到大量个人 image generation skill，但质量、密钥处理和服务依赖差异很大。本阶段不建议直接安装未经审查的随机 skill。

## 三个可选落地方案

### 方案 A：干净的小型文化墙生图站（推荐）

新建文化墙专用 UI 和一个很薄的 Node 服务端，从 GPT Image Playground 借用经过审查的协议适配思路和测试用例，不复制完整产品。

首版界面：

- 文化墙需求描述；
- 现场墙照片、Logo、参考图，最多 3 张；
- 3 个风格预设；
- 16:9、4:3、1:1 三个比例；
- 单次生成一张；
- 生成中／失败／成功状态；
- 下载、再次生成、将结果作为参考继续修改；
- 本地历史记录。

服务端保存 `API_BASE_URL`、`API_KEY` 和 `MODEL`，浏览器永远拿不到真实密钥。优先支持一个经实测的协议，不做“理论上兼容所有中转站”。

优点：范围最清楚、品牌和文化墙话术可控、安全边界正确、便于以后接生产化功能。缺点：需要自己完成一套小 UI 和服务端任务适配。

### 方案 B：裁剪 GPT Image Playground

以 MIT 项目为基础，删除分享广场、分类、批量操作、复杂参数和多协议 UI，只留下生图与历史。

必须同时完成：

- 将 API Key 从浏览器持久化迁到服务端；
- 删除导出文件中的凭证；
- 固定允许访问的中转站地址，避免开放代理；
- 把通用工作台重新包装成文化墙流程。

优点：最快得到成熟的参考图、历史、重试和局部编辑骨架。缺点：删减和安全改造并不少，容易继续背负通用工作台复杂度。

### 方案 C：前端 + LiteLLM／ComfyUI 网关

前端只调用统一内部 API，后端再连接多个中转站、本地模型或工作流。

优点：后期多模型、成本路由和复杂工作流最强。缺点：对当前单机获客版明显过重，应等真实调用量或模型需求出现后再选。

## 推荐的首版边界

无论选择 A 或 B，都建议明确：

- 首版验证的是“客户是否愿意提交墙体素材并等待文化墙效果图”，不是生产文件能力；
- 页面可以提示后续提供生产化服务，但不能把未实现的 SVG／CDR 能力包装成已完成；
- 不做登录、积分、支付、报价和公开素材社区；
- 不做 Agent、联网搜索、提示词广场、无限画布和批量并发；
- 不允许客户在浏览器中看到共享的中转站密钥；
- 真实开发开始前，先测试中转站的文生图、参考图、返回格式、超时和尺寸能力。

## 开发前必须取得的接口信息

不需要把密钥发到聊天里，只需在本地 `.env` 配置。需要确认：

1. 中转站 Base URL；
2. 模型 ID；
3. 文生图路径和请求示例；
4. 是否支持参考图／图片编辑；
5. 返回 URL 还是 Base64；
6. 支持的尺寸和图片数量；
7. 是否同步返回或需要轮询任务；
8. 超时、限流和计费规则。
