# 文化墙网站代码与功能审核

日期：2026-10-14。范围：本地当前工作区代码与 http://127.0.0.1:5173/，包括尚未提交的 Vectorizer.AI / 302 接入改动。

本轮未调用收费接口，未修改业务源码，未写入或删除真实项目。复现并发保存仅使用独立临时目录。当前 ECS 部署版本、302具体扣费明细、Illustrator/CorelDRAW/Photoshop实开未在本轮验证。

## 结论与评级

现有框架适合继续做小范围受邀测试，已经有局部描摹到可编辑SVG的闭环；付费结果保护、编辑保存和导出一致性尚需修复。继续保留现有底座和第三方引擎；当前优先级是让已有功能可靠，而不是继续增加模型或完整编辑器。

- P0：优先处理，涉及付费结果丢失、重复收费和费用控制。
- P1：下一轮修复，影响修改、尺寸、保存、导出等核心功能。
- P2：后续改善，降低学习和操作成本。
- 难度低/中/高为相对实现复杂度，不是工期或费用承诺。

## 结构判断

浏览器React负责生成表单、结果与最近8条本地历史；Fabric工作台负责毫米坐标下的对象编辑；Express负责邀请校验、供应商调用、项目和资源保存；RapidOCR和VTracer在本地Worker运行；Vectorizer经官方或302通道运行；SVG/PNG/PSD导出主要在浏览器完成。

这个规模使用Node单服务和账号隔离文件存储可以继续。主要问题在几个模块的衔接：付费返回→清洗→保存、图片→画布→多种导出、浏览器草稿→服务端版本。无需为修复这些问题先引入微服务、大型数据库或重新做生图系统。

## 建议执行顺序

第一批：F01—F03，先保护每一次已付费的结果，补任务记录、恢复和预算。不需要再购买服务。

第二批：F04—F10，保证修改不丢、同稿导出一致、尺寸可确认、项目不会被容量和并发保存卡住。重点保留原版SVG，不用再次调用上游来验证修复。

第三批：F11—F12及F14、F16、F18，提升半人工修复速度，优先复用Fabric现成能力。OCR擦除与高分辨率PSD不抢占前两批。

## 当前值得保留的能力

- 生图供应商适配器已经分开，前端无需接触密钥；不自动故障切换。
- Vectorizer服务端密钥不进入浏览器；真实SVG描摹和独立路径导出已跑通。
- 脚本、事件属性、外链等SVG内容受白名单处理，安全清洗不应直接删除。
- 项目、图片和SVG下载有受邀账号隔离；无需为1–3人试用先开发完整账号系统。
- RapidOCR和VTracer复用已有引擎；文本以text/tspan导出，位图以image导出，能力边界诚实。
- 源码模块规模仍可控，先修衔接和共享契约，比换底座更符合当前时效目标。
