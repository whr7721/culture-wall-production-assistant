# L2 文字层：本地验收与限制

## 证据判断

交接规格第六节的运行时证据优先于其前五节静态推断。梓恒实际 OCR 返回 `Baidu OCR`，不是前端默认字串 `RapidOCR`；其 `color` 固定为 `#111827`；无字底图实际走图像编辑上游且两次测试均失败退款。本站因此只借鉴 OCR 数据契约和 SVG 分层结构，没有把梓恒的引擎推断、无字底图方案或计费方式当成已验证事实。

使用 [`OSpoon/RapidOCRNode`](https://github.com/OSpoon/RapidOCRNode) v0.2.3（Apache-2.0，2026-10-13 仍更新）和 `onnxruntime-node` CPU 推理。它是遵循 RapidOCR 流程的**第三方 Node 实现，不是 RapidOCR 官方 Node 发行版**。本机 Node 26 可运行；该包要求 Node >=24，首次使用自动下载并校验上游模型。为避免 Windows 同进程加载两个 Sharp 原生版本，项目 Sharp 统一升级为 0.35.5。新依赖在 2GB ECS 上尚未验收，暂不推送服务器。

## 当前流程

打开项目，加入图片并选中它，点击“识别这张图片的文字”。服务端只接受当前受邀账号提交的图片，限单任务、每日 10 次；OCR 在工作线程运行。返回 `{ok,data:{items,engine,width,height}}`；每个 item 含 `id,index,text,bbox` 像素坐标、百分比 `x/y/w/h`、`score`、四点 `polygon`、`rotation`、估算 `fontSize`、`weight` 和**从框内图像主色采样的** `color`。界面叠加位置框，可逐项改字、勾选和改色，加入后按墙面毫米尺寸保存为独立文本对象。

整稿 SVG 的图片/背景使用 `<image>`，文本使用带 `<tspan>` 的 `<text>` 对象；字体未转曲。当前原图仍带旧字，加入文字对象后会叠在旧字上，须人工核对；无字底图尚未实施。百度 OCR 只留类型与拒绝路径，未配置密钥、未发出调用。无新的付费服务。

## 本机结果

- ACH 左面板原图：RapidOCR 识别 4 个文字框，分别为 `ACH`、`上海汽连网络科技有限公司`、`欧连`、`上海欧连电子科技有限公司`，耗时约 1.2 秒；四个框的采样文字颜色为白色。浏览器流程完成：识别、人工审核界面、加入、保存重开、下载 SVG；导出同时含 `<image>` 和可编辑 `<text>/<tspan>`。Inkscape 可打开并查询到独立文本对象。
- 4766×2690 整面候选图：识别 31 个文字框，约 1.8 秒；其中至少一个小字识别与人工阅读不一致。高置信度不等于文案正确；它也不能证明文字框已检测完整。
- 合成颜色样本验证了白字深底、深字白底的主色采样；`npm test` 38 项通过，`npm run build` 通过，浏览器验收命令 `npm run test:ocr-browser` 通过。验收材料在被 Git 忽略的 `output/ocr-acceptance/`。

## 下一道门槛

先让设计人员在一张有完整客户原文的真实平面稿上逐字核对：漏字/错字数、位置偏差、颜色偏差、人工修正时间。需要整张平面稿及文字正确性达到可接受水平后，再评估用现有 relay 编辑接口生成无字底图；该调用会产生费用，当前未执行。SVG 仍需在 Illustrator/CorelDRAW 实际验证字体替换、尺寸和对象可编辑性，Inkscape 通过不能代替这一关。
